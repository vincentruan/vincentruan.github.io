1. Build-Time Edge-TTS Audio Pipeline
TTS Engine + Integration High Confidence Medium Complexity
Description
Generate MP3 audio files during the GitHub Actions build using Edge-TTS (free, no API key, Azure-quality neural voices). After hexo generate completes, a post-build step iterates generated HTML, extracts clean text, and synthesizes audio. The MP3s deploy as static assets alongside HTML — zero per-listener cost, consistent quality regardless of browser, no API keys in config. Includes content-hash caching so unchanged posts skip regeneration (typical builds regenerate 1-3 MP3s instead of 143).
Basis
direct: GHA pipeline is npm ci → hexo generate → deploy with zero media processing. Edge-TTS is Python-based, free, no API key — matches the project's API-key-avoidance pattern (Utterances chosen over Gitalk for the same reason). reasoned: Build-time generation unlocks podcast distribution, offline listening, and CDN caching simultaneously — choosing client-side locks us out of all three.
Rationale
This is the highest-leverage architectural decision. Every other idea builds on it. Once the pipeline exists, every new post automatically gets audio on push — the marginal cost of the 144th post is zero. The build-vs-client choice determines whether the feature is a permanent infrastructure or a disposable experiment.
Downsides
Increases CI build time (~2 min per new/changed post). Edge-TTS voices may change without notice. Requires Python in the GHA environment. Audio files increase deploy artifact size.
2. Category-to-Voice Mapping via Config
Voice Style High Confidence Low Complexity
Description
Define a voice map in _config.next.yml that assigns a neural voice to each of the 16 categories. AI posts (45%, exploratory) get YunxiNeural (technical, slightly energetic); 成长思考 (personal essays) get XiaoxiaoNeural (warm, narrative); Java/架构 get YunjianNeural (authoritative, measured). Each profile specifies: voice name, rate multiplier, pitch shift, and inter-section pause length. Per-post override via front-matter voice: for edge cases — opt-in, like mathjax: true.
Basis
direct: 16 categories have distinct content personalities (voice-style dossier). No voice/tone/style fields exist in front-matter — clean slate. NexT config flag pattern (enable: true/false) established for every third-party service. reasoned: Adding voice_style: to 143 posts is manual burden that will never be maintained — categories are already maintained. One YAML block: change one line, all 64 AI posts switch voice.
Rationale
One voice for 143 posts across 16 categories creates monotony that kills long-term engagement. Category-based mapping captures the biggest voice diversity signal with zero per-post effort. New posts inherit automatically. The map is auditable, reviewable, diffable in git — following the tech-radar JSON-as-source-of-truth pattern.
Downsides
Categories are coarse — posts spanning multiple categories get one voice. Some categories have only 1-2 posts, making voice assignment arbitrary. Voice "personality" matching is subjective — what sounds "technical" to one listener may not to another.
3. Content Adaptation Layer ("Audio Edition")
Multimodal Pipeline High Confidence High Complexity
Description
A build-time before_post_render filter that generates an "audio edition" of each post — a parallel content representation where code blocks become conversational summaries ("这段代码实现了一个LRU缓存，核心思路是..."), tables become narrated comparisons ("Of the five structures compared, Array provides O(1) access while LinkedList requires O(n) traversal"), and Mermaid diagrams become verbal walkthroughs. A unified content descriptor JSON per post (source/data/descriptors/{slug}.json) serves as the single source of truth for TTS, RSS, search, and accessibility.
Basis
direct: 1,817 code blocks (66% of posts code-heavy), 1,366 table rows, 51 Mermaid diagrams. Reading these aloud verbatim is a known TTS failure mode. direct: Existing filter pipeline in scripts/ (mermaid-fence-to-tag at priority 9, strip-asset-prefix, fix-asset-paths) — the audio edition filter follows the exact same pattern. direct: Tech-radar JSON pattern proves data-as-source-of-truth works in this codebase.
Rationale
Without this adaptation layer, 66% of the blog is unlistenable. The descriptor compounds beyond TTS: RSS feeds can include summaries, search can index image descriptions, accessibility features consume the same data. Every feature that needs "what's in this post" reads from one source instead of building its own parser.
Downsides
Highest-complexity idea. Code summarization quality varies — may need LLM for good output or settle for heuristic extraction. Table-to-narrative is hard to generalize across different table structures. Descriptor adds build-time processing and storage.
4. AI Vision Pipeline for Image Narration
Multimodal Pipeline Medium Confidence High Complexity
Description
At build time, use a vision model (Claude or GPT-4V) to generate 1-2 sentence descriptions for each of the 1,219 images. Store as sidecar JSON in source/data/image-descriptions/{post-slug}.json. The Content Adaptation Layer (Idea 3) reads these descriptions when generating the audio edition. For the "红黑树" post with 30 diagrams, each illustration gets a spoken description: "This shows a red-black tree with node 7 as root..." Algorithm diagrams get structural descriptions; UI screenshots get content descriptions; flowcharts get path descriptions.
Basis
direct: 1,219 image references, 633 actual image files. Posts like "30张图带你彻底理解红黑树" are fundamentally visual — without descriptions, the audio version loses the entire point. external: Claude Vision and GPT-4V can describe technical diagrams with high accuracy. Cost: ~$2-5 for all 633 images at current rates.
Rationale
80% of posts contain images. For visual-heavy posts (algorithms, architecture), images ARE the content. Without narration, these posts are half-empty in audio form. The vision API cost is a one-time build-time expense, and descriptions cache with the content-hash system (Idea 1).
Downsides
Requires API key for vision service (tension with the project's API-key-avoidance pattern — but build-time only, in GitHub Secrets). Description quality may vary for complex diagrams. External image URLs (many posts reference external images) can't be processed. Regeneration needed when images change.
5. Podcast RSS + Invisible Audio Player
Integration + UX High Confidence Medium Complexity
Description
Two complementary moves in one idea. First: generate an RSS feed at /feed/audio.xml with <enclosure> tags for each post's MP3 — the blog becomes a podcast subscribable in Apple Podcasts, Spotify, and Overcast. Second: inject an invisible audio player via NexT's postBodyEnd + Media Session API — car Bluetooth shows it as a track, phone lock screen shows play/pause/skip, browser media keys work globally. No visible player UI needed for the primary listening scenario (driving/bedtime).
Basis
direct: Permalink pattern :year/:month/:day/:name/ maps naturally to podcast episode URLs. 12 NexT injection points via source/_data/ are unused. external: Podcast RSS spec requires <enclosure> tags — once the feed has enclosures, any podcast app subscribes. reasoned: The user said "driving and bedtime" — that's a podcast, not a web player. Nobody opens a browser at 30km/h or in bed.
Rationale
A custom audio player on the blog page serves readers who also want audio. A podcast feed serves listeners who may never read the blog. The audio files already exist from Idea 1 — adding enclosures is ~20 lines of code. The Media Session API integration means the driving scenario works with zero custom UI — the phone's native media controls become the blog's audio interface.
Downsides
Podcast directory submission requires manual setup (Apple, Spotify). RSS enclosures increase feed size significantly. Media Session API behavior varies across browsers and OS. "Invisible player" may confuse users who expect a visible control.
6. Layered Listening (概览 / 详解 / 深入)
Listening UX High Confidence Medium Complexity
Description
Like museum audio guides offering 3 narration layers per exhibit, each post gets three listening depths: "概览" (overview — reads only the description field, ~1 min), "详解" (detailed — prose + code summaries + table narrations, ~8 min), "深入" (deep dive — full content with structural audio cues). A 15-second pre-listening briefing auto-generated from front-matter plays first: category, content structure, key takeaway. The layer selector lives on the audio player. For 84 posts with descriptions, the overview layer is available today with zero additional authoring.
Basis
direct: description field exists on 84 posts (59%) — 2-4 sentence abstracts. reasoned: Museum audio guides face the identical structural problem — one exhibit serving passerby, learner, and expert through the same audio channel. Their solution (layered depth, user-selected) is battle-tested across millions of visitors. reasoned: Bedtime favors "概览" (short, conceptual); commute favors "详解"; study session uses "深入".
Rationale
Audio consumption is commitment-heavy — you can't skim audio the way you skim text. Without layers, listeners either bounce (never trying audio) or commit to a 40-minute architecture post when they only have 15 minutes. The pre-listening briefing eliminates the "I don't know what I'm listening to" disorientation. One audio pipeline, three consumption modes, zero additional content for posts that already have descriptions.
Downsides
Requires generating 3 audio versions per post (3x storage and build time). The 59 posts without description get no overview layer unless descriptions are backfilled. Layer selection adds UI complexity. The "depth" levels need clear boundaries — what's "detailed" vs "deep" for a given post?
7. Hybrid TTS Fallback
TTS Engine Medium Confidence Low Complexity
Description
When a post loads, a small JS widget checks if a pre-generated audio file exists at /audio/{year}/{month}/{day}/{name}.mp3. If yes, play it (Edge-TTS quality). If no (new post not yet deployed, or first visit), fall back to the Web Speech API for instant browser-native narration — lower quality, but available immediately with zero latency. This gives the author instant feedback while writing; the reader gets high-quality audio once deployed.
Basis
reasoned: The two engines solve different problems — Web Speech is "instant, local, preview" while Edge-TTS is "high-quality, deployed, permanent." During authoring, the writer wants to hear their post immediately to check flow — waiting for a GHA deploy cycle (2-5 minutes) to test narration is a dealbreaker. direct: Web Speech API is free and browser-native; Edge-TTS is free and no-key.
Rationale
Removes the "pick one TTS engine" decision. Degrades gracefully: if Edge-TTS fails in CI, the post still has Web Speech fallback; if Web Speech is unavailable (older browser), the post still has Edge-TTS. The author gets instant feedback; the reader gets production quality. Zero additional cost since both are free.
Downsides
Two different voice qualities for the same post may feel inconsistent. Web Speech API Chinese quality varies wildly by browser/OS — may sound worse than no audio at all on some devices. Adds complexity to the player JS for engine detection and switching.
